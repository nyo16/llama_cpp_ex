# Benchmark Results — audit remediation, Phase 7 `[perf]`

Old-vs-new for the two slot-scheduling fixes that landed in this phase, plus the
first numbers for prompts above 220 tokens.

- **Repo**: audit-remediation, working tree over `3f9b554`
- **llama.cpp**: `ff067f76d`
- **Hardware**: Apple M4 Max, 64 GB unified memory, 16 cores
- **Backend**: Metal (`LLAMA_BACKEND=metal MIX_ENV=bench`)
- **Runtime**: Elixir 1.20.0, Erlang 29.0, JIT on
- **Model** (server benches only): SmolLM2-135M-Instruct-Q8_0
- **Date**: 2026-07-27

The two `Slots` benchmarks need no model: `LlamaCppEx.Server.Slots` only compares
token ids. The pre-optimisation implementations are copied verbatim into
`Bench.SlotsOld` in `bench/slots.exs` and run head-to-head on the same VM, same
heap, same inputs — so "old" here is a measurement, not a number carried over
from another branch.

**Read the reduction column, not the wall-clock column.** At these magnitudes
wall time moves ±2x between runs with GC and scheduler noise; reduction counts
came out byte-identical across three runs.

## `Slots.donor_prefix_match/2` on a `:generating` slot

Cost **per candidate slot**; the server pays it once per busy slot per request,
so multiply by `n_parallel - 1`.

Common case — an unrelated request, so the walk dies 8 tokens in. Old still
copied the whole prompt to get there.

| Prompt | old | new | reductions old → new | memory old → new |
|---|---|---|---|---|
| 220 tok | 430 ns | 17 ns | 207 → 12 (17.3x) | 3.30 KB → 0.02 KB |
| 4k | 6.18 µs | 0.048 µs | 2630 → 12 (219x) | 8.20 KB → 0.02 KB |
| 8k | 14.59 µs | 0.039 µs | 4000 → 12 (334x) | 104.36 KB → 0.02 KB |
| 32k | 96.48 µs | 0.022 µs | 1080 → 12 (90x) | 510.02 KB → 0.02 KB |

Worst case — the whole prompt matches, so the generated tail is reached and the
new code pays for the `Enum.reverse/1` it was avoiding.

| Prompt | old | new | reductions old → new | memory old → new |
|---|---|---|---|---|
| 220 tok | 883 ns | 659 ns | 527 → 481 (1.10x) | 4.72 KB → 1.33 KB |
| 4k | 12.57 µs | 5.80 µs | 6870 → 4240 (1.62x) | 6.20 KB → 2.06 KB |
| 8k | 27.07 µs | 10.91 µs | 12310 → 8330 (1.48x) | 102.36 KB → 2.06 KB |
| 32k | 131.38 µs | 35.01 µs | 33970 → 32910 (1.03x) | 508.02 KB → 2.06 KB |

Old at 4k (6.18 µs) and 32k (96.48 µs) reproduces the audit's 6.05 µs / 85.4 µs
on different hardware, so the two measurements corroborate each other.

The 32k common-case reduction count for old (1080) is lower than 8k's (4000)
because `++` traps at that length and the BIF's reduction accounting undercounts
the restart. Wall time and allocated bytes both scale linearly as expected —
510 KB is exactly 32768 × 16 B — so only that one cell is an artifact.

## `Slots.pick_cached_slot/2` + the caller's LCP

Cost **per request**. Eight idle slots, one holding the request's own prompt, so
the winner's LCP is full length — which is exactly the walk the old caller
repeated at `server.ex:760`.

| Prompt | old | new | reductions old → new |
|---|---|---|---|
| 220 tok | 976 ns | 670 ns | 625 → 402 (1.55x) |
| 4k | 41.73 µs | 23.10 µs | 8620 → 4520 (1.91x) |
| 8k | 82.88 µs | 62.34 µs | 17070 → 8870 (1.92x) |
| 32k | 338.92 µs | 264.90 µs | 67760 → 34980 (1.94x) |

The reduction ratio is 1.91–1.94x at every size above 220 tokens and the saving
is linear in the prompt (4.10 K / 8.20 K / 32.77 K reductions), which is the
signature of removing exactly one full-length LCP walk. Allocation is unchanged
at 448 B either way — this fix buys time, not memory.

## `server_generate` — the >1k regime, end to end

`bench/server_generate.exs`, `n_parallel: 1`, `n_ctx: 40960`, greedy. Prompts
built by `Bench.Helpers.long_prompts/1`, verified to tokenize to exactly 1024 /
8192 / 32768 tokens under the model's own vocab.

| Input | tokens | 32-token generate | 128-token generate |
|---|---|---|---|
| short | 5 | 61.97 ms | 256.05 ms |
| medium | 101 | 61.44 ms | 266.08 ms |
| long | 201 | 61.44 ms | 254.49 ms |
| 1k | 1024 | 67.83 ms | 262.82 ms |
| 8k | 8192 | 88.83 ms | 327.68 ms |
| 32k | 32768 | 156.35 ms | 525.11 ms |

These are absolute numbers on new code. There is no same-machine "before" for
this script: producing one would need the old `lib/` built against the old NIF,
and the scheduling fixes above are microseconds against tens of milliseconds of
GPU work — below this benchmark's noise floor by three orders of magnitude. Its
job is to make the >1k regime measurable at all, and to catch a future
regression that *is* large enough to see here.

## No regression at 220 tokens

Both fixes are a win at the size everything was previously measured at, not just
at the sizes they were written for: 1.10–17.3x fewer reductions for
`donor_prefix_match/2` and 1.55x for `pick_cached_slot/2` at 220 tokens. Neither
change has an input class where the new code does more work than the old.

## Reproduce

```bash
MIX_ENV=bench mix run bench/slots.exs

MIX_ENV=bench LLAMA_BACKEND=metal GGML_METAL_NO_RESIDENCY=1 \
  LLAMA_MODEL_PATH=models/SmolLM2-135M-Instruct-Q8_0.gguf \
  mix run bench/server_generate.exs
```
